Economy gameplay ideas — September 17, 2026

Make the starter laptop the entry to a small, silly business: do a job, earn coins, buy equipment, automate part of the job, and spend the proceeds on a more personal office. Start with short playable jobs and one production loop. All mechanics and prices below are proposals; this review changes no gameplay or balances.

The current implementation provides 250 welcome coins, daily bonuses of 10/15/20/25/30/35/50, and a shared 100-coin daily game allowance. New players receive a Cafe table and Laptop with zero recorded purchase cost. The personal shop contains 261 item types costing 25–1,100 coins, or 44,280 for one of each. Those catalogue totals include the two starter item types. Sources: [reward rules](../packages/shared/src/economy.ts), [accounts and starter grants](../apps/server/src/economy/economy-store.ts), [catalogue](../packages/shared/src/asset-catalog.json).

There is useful artwork already: the garden bed costs 140, apple tree and potted orange tree 75 each, coffee bar 480, vending machine 240, and interactive toys 160 each. The laptop and these plants/food stations have no earning or production behavior. Whiteboards and checklists have editable state; toys provide temporary effects or messages. Server racks, printers, ducks, robots, and drones were not found by catalogue ID/name and would require artwork. Sources: [catalogue](../packages/shared/src/asset-catalog.json), [work objects](../packages/shared/src/work-objects.ts), [toys](../packages/shared/src/special-props.ts).

These are fictional jobs. Paying for real commits, messages, meetings, or checking off arbitrary work tasks would reward volume and turn the workplace into a coin grind. Existing checklist completion should remain a work action.

The automation should be visible and useful. Begin with manual controls and a few instructions such as “if ripe, harvest; otherwise water,” then add loops, routing, and small queues. A visual editor and optional text editor can describe the same game program. Better programs reduce wasted steps and handle harder orders. Cosmetic reactions make mistakes funny; a mistake pauses that machine or loses the round, rather than destroying furniture or creating debt.

For inspiration, [Bitburner](https://store.steampowered.com/app/1812820/Bitburner/) makes JavaScript automation part of progression; [Screeps](https://docs.screeps.com/scripting-basics.html) runs game scripts in bounded ticks, including while players are offline; [The Farmer Was Replaced](https://store.steampowered.com/app/2060160/The_Farmer_Was_Replaced/) connects programmed farming to technology unlocks. My design inference is to borrow visible automation and gradual capability growth, scaled to short office-game sessions. These references do not establish suitable coin rates for this game.

Players also need reasons to spend after furnishing a desk. The following price bands are starting points for playtesting, not catalogue changes.

| Purchase | Proposed price | Reason to buy again or keep saving |
| --- | ---: | --- |
| Automation modules | 300–1,200 | Unlock irrigation, an order queue, or a new machine function. Better equipment supports more interesting programs and fewer manual steps. |
| New personal cosmetics | 75–600 | Rubber ducks, ridiculous keyboards, bot costumes, terminal themes, and new celebrations. Keep existing free avatar options and item variants free. |
| Optional consumables | 5–25 | Special confetti patterns, party snacks, or a temporary cosmetic coffee effect. Sell a separate consumable; existing decorative food and ordinary toy use retain their behavior. |
| Shared destinations | 1,200–5,000 as a project budget | A server greenhouse, rooftop cafe, elaborate arcade, or incident room creates a visible group saving goal. Actual cost comes from the purchased components and construction. |
| Business relaunch | Price to establish after playtesting | After finishing a business's challenge set, pay to launch a different themed version and earn a display trophy. Restart only that business's progress, preserving the wallet, home, and unrelated equipment. |

Automation modules are investments that can eventually pay for themselves. Cosmetics, consumables, and optional themed projects absorb the resulting surplus. Shared donations move coins into a public fund; the subsequent purchase or construction actually spends them. Team projects continue through the existing public economy, with paid construction for every role. Sources: [public economy](../packages/shared/src/public-economy.ts), [construction pricing](../apps/server/src/economy/project-quote.ts).

To add actual income while preserving gradual progression, I would test this budget:

- Keep the 250 welcome grant and daily bonus schedule.
- Put existing games and new active jobs in one shared 100-coin daily allowance. A new activity does not receive its own allowance.
- Add at most 25 production coins per player per UTC day, shared by all farms, coffee pipelines, and SaaS businesses. Manual and scripted production draw from the same pool. Buying more machines expands options without multiplying that ceiling.
- Limit unattended production to one day's work and a 25-coin output buffer. Account for it using server time and persist settlement, so a restart or repeated collection cannot create another day's output. Do not require an open browser tab.
- A contract is either active or production work when issued, and pays once. A script cannot replay an active coffee round as a second production payout.

This raises the mature maximum from 150 to 175 coins per day, about 17%, before purchases. It is a proposal, not an enacted increase. As an optimistic illustration, a 500-coin upgrade generating the full additional 25 every day takes 20 days to earn back its cost. Smaller output, input costs, or skipped days extend that; an upgrade adds no income if another machine already fills the production allowance. The extra income should ship with attractive spending options. Avoid unlimited idle compounding and mandatory maintenance bills.

Personal production should use personally owned upgrades and return coins to the player's wallet. Shared terminals can provide access to a minigame without owning its business. Keep shared production out of the first release so it cannot become an accidental route from public funds into private income.

The best first release is the laptop plus bug bounties, one garden production loop, one automation module, and a small set of optional cosmetics. Allow access through the owned laptop in inventory as well as a placed laptop, so starting a job does not depend on getting a public placement approved. Aim to test active rounds around two to four minutes; that is a design target, not measured duration. Coffee is the next expansion. SaaS and bot arenas should follow only once running a little program is fun in its own right.

Several implementation details affect that scope:

- Existing game rewards are tied to round IDs, lines/wins, and saved scores. New jobs need their own completion evidence while sharing the active reward allowance; do not represent a harvest as fictitious cleared lines. Extend the canonical settlement path and persisted transaction kinds together. Sources: [reward settlement and restore validation](../apps/server/src/economy/economy-store.ts), [database transaction constraints](../apps/server/src/persistence/entities/workspace-entities.ts).
- Machine progress and programs must follow the owned item through storage and replacement. An owned asset currently has purchase and placement data, while work-object state belongs to a placed object; storing a machine must neither erase its program nor reset its payout eligibility. Sources: [owned assets](../packages/shared/src/economy.ts), [work-object state](../packages/shared/src/work-objects.ts).
- Use a bounded game-command interpreter with server-validated outcomes. Scripts operate on fictional machines, with limits on steps, output, and elapsed work. They should not execute arbitrary host code or access the real filesystem, network, or connected repositories.
- Preserve recorded purchase costs: free starter items still resell for zero, and paid durable items return one-third of their recorded cost. Give purchased upgrades their own receipts. Harvested output fulfills production orders; it does not become a free catalogue item with an invented resale price. Source: [resale calculation](../packages/shared/src/public-economy.ts).
- Special-prop cooldowns currently live in memory and clear on reset. They are useful for effects, but money needs persisted completion receipts and daily accounting. Source: [toy interactions](../apps/server/src/world/special-props.ts).

Verification performed for this assessment: catalogue counts, totals, matching assets, and reward arithmetic were recomputed. All 50 tests passed across economy-store, economy-rewards, starter-inventory, game-rewards, world-runtime.special-props, and world-runtime.player-assets. Those existing tests cover the current reward rules, repeat payments, UTC reset, starter ownership, placement, and toy interactions; they do not validate proposed gameplay.

Only this proposal document was added. No development server was started, and no new browser gameplay, PostgreSQL persistence run, or player telemetry study was performed. Proposed prices, session lengths, scripting usability, and demand for repeat purchases still require a playable prototype and balance testing.
