# Falling Blocks networking

Falling Blocks runs one rules engine in both the client and server. The client applies controls immediately and advances the simulation clock locally at 50 ms intervals. The server runs the same rules and remains authoritative for attacks, results, statistics, and rewards. This follows the client prediction and reconciliation model described by [Gaffer on Games](https://gafferongames.com/post/what_every_programmer_needs_to_know_about_game_networking/).

Every server board state includes the complete simulation snapshot, a server timestamp, and acknowledged input sequences for the player's active input sessions. The client restores a snapshot, replays unacknowledged controls at their recorded local times, and advances to the present. It keeps a local state that is at most one gravity row ahead when the rest of the simulation agrees, avoiding visible backward steps from routine network delay. Server attacks and other real differences replace the prediction. The full snapshot includes the piece queue, random state, timers, lock state, and scoring state so the replay continues from the same rules state. [State synchronization](https://www.gafferongames.com/post/state_synchronization/) describes why the nonvisual state matters.

Inputs carry a sequence and a session ID. The server ignores duplicate sequences within each session, so reconnect retries cannot execute a control twice and separate tabs can control the same round. The client holds up to 256 unacknowledged inputs and resends them when the connection returns. The transport coalesces board snapshots within 100 ms and sends the latest acknowledged sequence with the newest board. A disconnected player's round continues for 15 seconds before the server ends it. If an attack or delayed command changes the authoritative outcome, the client corrects its board; a disconnected client cannot guarantee its predicted outcome.

The WebSocket client already limits its outgoing buffer using `bufferedAmount`, which reports queued bytes as documented by [MDN](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/bufferedAmount). Server snapshots still contain the full board and simulation state. Network byte volume and correction frequency should be measured on real remote links before changing snapshot frequency or encoding.
