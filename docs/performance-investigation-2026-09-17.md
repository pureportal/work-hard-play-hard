The application has worthwhile performance opportunities within its existing architecture. Prioritize avatar decoding/readback, synchronous pathfinding, repeated settings cloning during movement, and static asset delivery. The measured warm scene does not justify a renderer or framework migration.

This is an investigation dated 17 September 2026. Application code, configuration, dependencies, and original images were left unchanged. Four probe scripts, this assessment, and isolated build/profiling artifacts were added. Existing work in the checkout was preserved.

**Baseline discrepancy:** the task specifies **260 units/second**, but [character.ts](../packages/shared/src/character.ts) currently exports `CHARACTER_WALK_SPEED = 350` at line 42. The server uses it through [movement-speed.ts](../apps/server/src/world/movement-speed.ts), which also implements distance-dependent destination travel up to 750. Neither was changed. The recorded runtime probes therefore describe the observed 350 baseline, not a validated 260 baseline. Resolve that discrepancy before an optimization comparison; retain 260 as the intended authoritative walking speed and preserve the existing movement modes. Increasing distance traveled is not a latency improvement.

The installed stack is React/React DOM 19.2.8, PixiJS 8.20.1, Vite 8.2.2, Node 24.14.1, Fastify 5.12.1, `@fastify/websocket` 11.3.0, `ws` 8.21.3, MikroORM 7.1.14/PostgreSQL, Sharp 0.35.4, and Zod 4.5.1. These are installed versions, not package manifest ranges. The same client is packaged through Tauri for desktop/Android. [Inventory and source revision](../artifacts/performance-investigation-2026-09-17/inventory.json).

The client restores its HTTP session, starts preloading the world module, obtains the bootstrap, mounts the workspace, and opens its WebSocket. React manages UI and incoming state; an imperative Pixi renderer animates the world. Games run on the authoritative Node runtime. Meetings use WebSocket signaling and direct WebRTC peer connections for media. PostgreSQL persistence runs separately from ordinary movement commands.

Useful work is already present: lazy world/panel/game imports, game preloading from lobbies, lossless WebP delivery copies, small world previews, cropped static avatar composition, byte-budgeted caches with pending-request sharing, shared avatar GPU textures, active-mover tracking, floor-scoped snapshots, a five-second idle heartbeat, shared event serialization, and socket backpressure limits. Recommendations below build on those paths.

Start by recording the validation metrics for each selected item. Keep one stable source snapshot, device, power mode, scene, cache condition, and workload for paired comparisons. This is especially important because the workspace and host are shared.

**Loading measurements support smaller inputs more strongly than a new asset framework.** The isolated production build completed in 48.27 seconds, including source maps and public-directory copying. This is build time, not user startup time. Its existing large-chunk warning concerns the deferred world-artwork module.

| Build measurement | Bytes | Gzip bytes |
| --- | ---: | ---: |
| Entry plus recursively traversed static JavaScript imports | 731,038 | 222,057 |
| Image lookup chunk included in those imports | 220,473 | 86,368 |
| Deferred world-artwork chunk | 605,893 | 33,586 |
| Deferred WorldCanvas chunk, excluding its dependencies | 340,727 | 99,371 |

The gzip values use Node's default compression settings and include tiny source-map references; they are estimates of compressed bodies, not observed HTTP transfer sizes. Brotli produced 189,979 bytes for the initial JavaScript set, 14.4% below gzip. The static files can be compressed without adding a client runtime dependency.

[nginx.conf](../apps/client/nginx.conf) sets immutable caching for `/optimized-images/`, but contains no explicit JS/CSS gzip configuration or immutable `/assets/` policy. This is a confirmed configuration omission, not proof that a deployed CDN or enclosing Nginx configuration fails to compress. Verify the deployed response first. Nginx compression defaults to off and its default additional type configuration does not cover JS/CSS. Keep HTML revalidatable and long-lived caching confined to content-hashed assets. Do not spend CPU recompressing WebP. [Nginx gzip documentation](https://nginx.org/en/docs/http/ngx_http_gzip_module.html).

[optimized-images.ts](../apps/client/src/optimized-images.ts) imports the entire generated lookup object; [CharacterPreview](../apps/client/src/components/CharacterPreview.tsx) brings its loader into startup. A JSON partition experiment measured character entries at 62,566 bytes/16,148 gzip and world entries at 157,375 bytes/69,785 gzip. Splitting at the character/world consumer boundary could defer approximately 70 kB compressed from initial loading; that is an estimate from separately encoded JSON, not a rebuilt bundle saving. World metadata can later be partitioned by needed assets if traces justify it. Do not preload the whole catalog. Existing dynamic imports already receive Vite's dependency-preload handling. [Partition evidence](../artifacts/performance-investigation-2026-09-17/manifest-partitions.json), [Vite build optimizations](https://vite.dev/guide/features#build-optimizations).

The delivery manifest contains 814 character layers, 885 world atlases and three architecture atlases. Character originals total 415.1 MB versus 192.1 MB for their lossless delivery copies; world originals total 45.9 MB versus 16.6 MB, plus 24.6 MB of preview copies. These are whole-catalog totals, **not startup downloads**. Sources are already compressed well enough that reducing which pixels are needed deserves priority over another blanket format conversion.

Each avatar layer still loads a **960 × 3840** image, including color and depth, even for a 48 × 48 portrait. [character-layers.ts](../apps/client/src/character-layers.ts) limits source loading to two operations, and [image-decoding.ts](../apps/client/src/image-decoding.ts) serializes explicit `decode()` calls across world and character images. These controls constrain pressure but do not reduce decoded image size. Raising concurrency without a memory/decode profile is not a safe assumption of improvement.

The existing avatar diagnostic recorded: Face 12.43 s/79 decodes, Hair 6.19 s/34 decodes, Tops 4.02 s/28 decodes, Headwear 3.77 s/28 decodes. The first phase also includes unfinished people portraits. These are one-run instrumented fixture timings on a busy host, not isolated per-option costs or a production service-level claim. No decode errors were recorded. CPU samples prominently identify `getImageData`, including roughly 3.44 s of sampled time across the Hair phase. The diagnostic subsequently failed because it expects animation buttons, whereas the current editor uses selects; its later save/reload/movement assertions did not run. [Diagnostic measurements](../artifacts/performance-investigation-2026-09-17/browser/measurements.json), [source-mapped profile attribution](../artifacts/performance-investigation-2026-09-17/profile-attribution.json).

The independent compact-layer experiment retained the first idle frame in all four directions, with corresponding depth frames, in **120 × 960** delivery images. All 40 retained tiles across five default layers matched original visible RGB and alpha, including the depth data. It reduced those five WebPs by **96.16%** without resizing them. This validates the source-size opportunity only; it does not establish an integrated startup speedup, and the rest of the wardrobe remains to be checked. Full animation atlases remain necessary for animated previews/world sprites. Extend the existing generation/check pipeline and choose the appropriate derivative for each use. [Experiment and copies](../artifacts/performance-investigation-2026-09-17/portrait-experiment/measurements.json), [Sharp lossless output](https://sharp.pixelplumbing.com/api-output/).

Full-atlas composition is another candidate for a browser worker using transferable pixel buffers or OffscreenCanvas. Move decoding/readback and composition together where supported; moving just the final loop would leave much of the observed cost on the main thread. Transfer overhead and GPU upload remain. Verify identical pixels and the actual Tauri WebViews before choosing the implementation. [Browser worker guidance](https://web.dev/articles/off-main-thread).

**Movement latency has distinguishable client, scheduling, network, and server components.** [WorldRuntime](../apps/server/src/world/world-runtime.ts) schedules 50 ms ticks, publishes changed floors every second tick, and sends idle snapshots every 100 ticks. [useRealtime](../apps/client/src/hooks/useRealtime.ts) parses snapshots and updates React state. [WorldCanvas](../apps/client/src/components/WorldCanvas.tsx), line 1280 onward, moves both local and remote sprites toward the latest target using exponential smoothing with a 67 ms time constant. There is no local prediction or timestamped remote snapshot interpolation buffer in that path.

The relevant sequence is input dispatch → outgoing socket → server arrival/queue → simulation and publication → incoming socket/JSON → React update → interpolated frame. Tick and publication waits are related phases: do not add fixed 50 ms and 100 ms delays to every input. The publication phase can itself introduce up to roughly 100 ms before transport, contention and rendering. The 67 ms smoothing constant is not a fixed network delay; a stationary target reaches about 95% convergence after 201 ms.

The dedicated production-client probe used one visible player, identical portrait appearances, a 1440 × 1000 viewport at DPR 1, six seconds idle and sixteen alternating movement probes. Requests were intercepted and supplied from disk/an in-process runtime. It bypasses real sockets, TLS, Fastify validation, PostgreSQL and the WAN.

| Artificial one-way delay | First observed movement p50 / p95 | Snapshot arrival p50 / p95 | Direct movement-handler p95 |
| --- | ---: | ---: | ---: |
| 0 ms | 96 / 170 ms | 90 / 161 ms | 0.11 ms |
| 40 ms each direction | 146 / 266 ms | 141 / 256 ms | 0.19 ms |

First motion means more than 0.5 world units of displayed displacement after dispatched keyboard input. These sixteen-sample distributions include scheduling and the first-gesture audio cost. The delay injection is a sensitivity experiment, **not measured Internet RTT**; phase/caching differences prevent interpreting the difference between medians as a precise transport contribution. [Browser probe data](../artifacts/performance-investigation-2026-09-17/frames.json).

Local prediction should use acknowledged input sequences/timing and the same normalized movement, collision and travel rules. Server snapshots currently carry a world tick but not the last processed movement input acknowledgment needed for robust replay. Preserve server authority over access, seating, carrying, teleports and game outcomes. Remote players can use timestamped buffered interpolation; that trades a deliberate display delay for smoother jitter handling. Neither requires a networking framework replacement. [Prediction and reconciliation](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html), [entity interpolation](https://www.gabrielgambetta.com/entity-interpolation.html).

**Server CPU costs become material before game input logic does in these fixtures.** The final in-process benchmark warmed 100 ticks, then timed 1,000 ticks per scenario with cached serialization included. Populations 13, 50 and 100 use the same test floor with synthetic additional members. These are elapsed CPU-work measurements, not a socket load test or a capacity guarantee.

| Players moving / players on floor | Tick p50 | Tick p95 | Tick p99 | JSON sent per peer per simulated second |
| --- | ---: | ---: | ---: | ---: |
| 0 / 13 | 0.001 ms | 0.005 ms | 0.042 ms | 0.40 kB |
| 1 / 13 | 0.36 ms | 1.00 ms | 3.01 ms | 19.93 kB |
| 13 / 13 | 1.60 ms | 3.75 ms | 6.53 ms | 20.04 kB |
| 50 / 50 | 7.08 ms | 12.32 ms | 15.40 ms | 74.61 kB |
| 100 / 100 | 16.13 ms | 26.78 ms | 31.16 ms | 148.39 kB |

The 100-player case sends approximately 14.84 MB/s in aggregate JSON at the existing snapshot rate, before WebSocket/TLS overhead. Even one mover sends the full current floor roster to each peer. Consider changed-player deltas only after measuring real crowd sizes, with explicit enter/leave data and complete resynchronization on reconnect. Binary serialization or compression will not remove redundant full-state updates. `ws` specifically recommends workload testing before enabling per-message compression because of CPU/memory overhead; this server already disables it. [Server measurements](../artifacts/performance-investigation-2026-09-17/server.json), [ws compression guidance](https://github.com/websockets/ws/blob/master/README.md#websocket-compression).

[findPath](../apps/server/src/world/pathfinding.ts) already uses a binary heap and limits visited cells to 50,000. Searching from (410,650) to (450,650) took 0.15 ms median, but (1250,700) took 67.31 ms median/100.91 ms p95 and (735,350) took 61.23/75.53 ms. Searches were warmed five times and sampled forty times. [collision.ts](../apps/server/src/world/collision.ts) caches collider construction by layout revision, but scans the collider list for each occupancy query. A spatial broad phase or revision-specific static navigation data can reduce that repeated work while retaining the current exact checks and path semantics. A new heap package would duplicate an existing optimization.

The CPU profile also directly links substantial `structuredClone` samples to `getGameSettings → userHasRoomAccess → getRoomAccessIds → advancePlayerStep`. [getGameSettings](../apps/server/src/economy/economy-store.ts) clones the settings on each read. Each movement substep recomputes room access and scans all players for capacity. Use stable, versioned internal settings reads and maintain occupancy counts as players actually enter/leave; a frozen capacity snapshot for the whole tick could incorrectly admit two players to the final seat. Retain cloning where an external mutable boundary requires it. [Clone call stacks](../artifacts/performance-investigation-2026-09-17/clone-attribution.json).

If algorithm/data-flow improvements leave long searches, evaluate a bounded Node worker pool. Preserve ordering, cancellation and layout/access revision checks when applying results. Workers isolate CPU work but do not inherently reduce search latency. The timer currently advances by a fixed 50 ms regardless of elapsed wall time, so event-loop stalls can also make simulation fall behind; measure scheduler lateness before designing bounded catch-up. [Node performance hooks](https://nodejs.org/docs/latest-v24.x/api/perf_hooks.html), [worker threads](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html).

Falling Blocks' 1,000 alternating lateral inputs, after 100 warm-up inputs without simulated gravity, took **0.009 ms median/0.025 ms p95** inside the game handler and emitted one roughly 1,133-byte private `game.state` per input. At its 32 ms horizontal repeat interval that state alone is about 35 kB/s while held. This does not measure attacks, completion, browser board updates, or network round trips. Commands apply immediately on receipt; gravity uses the world update tick. Keep intentional 110 ms initial repeat delay and gameplay rules separate from latency. Chess already runs Stockfish in a child process, but [chess-bot.ts](../apps/server/src/games/chess-bot.ts) starts a new engine per search. A bounded reusable engine pool is conditional on measured startup overhead; preserve search difficulty/time budgets and cancellation. Tic-tac-toe, chess, and real multiplayer end-to-end latency were inspected but not benchmarked.

**Rendering measurements show good warm consistency in a limited scene, with expensive cold work.** Chromium 148 reported an AMD Radeon RX 9070 through ANGLE. Node ran on an AMD Ryzen Z2 Go. The probe referenced 933 scene nodes and 41 unique texture sources, about **191 MiB** at width × height × four bytes. This is an estimate of referenced texture pixels, not measured VRAM; mipmaps, driver allocations, CPU images/canvases and caches are additional.

| Browser phase, no artificial delay | Frame interval p50 / p95 / p99 | Worst interval | Renderer CPU submission p95 |
| --- | ---: | ---: | ---: |
| Warm idle, 360 intervals | 16.7 / 17.3 / 17.6 ms | 17.7 ms | 2.0 ms |
| Movement, 779 intervals | 16.7 / 17.2 / 17.5 ms | 83.3 ms | 2.2 ms |

The delayed run was similar at the median with one 67.1 ms interval. Neither establishes GPU execution time or displayed frames on a physical device. Startup included long tasks of 574, 236 and 162 ms in the first dedicated run, with a maximum instrumented canvas readback of 536 ms. First-avatar readiness was 2.96 s in that run and 0.97 s in the next fresh context; OS/driver/process warming and shared-host activity make these unsuitable as cold-versus-warm speedup claims. [Frame summary](../artifacts/performance-investigation-2026-09-17/summary.json).

[WorldAssetTextures](../apps/client/src/world-asset-textures.ts) holds source images, textures, frames and optional alpha masks until destruction. Floor changes destroy views but do not apply a byte budget to this cache. Explicitly manage references/eviction and stage uploads with Pixi's existing prepare system. Evaluate culling on whole object containers with bounds that include shadows, labels and animation extents. Skip offscreen animation work while preserving its time-based phase. Culling can hurt a CPU-bound scene, and texture caching of complex static regions increases memory; measure both. Keep transparency/depth ordering, rotations, hit testing and visual details intact. [Pixi performance guidance](https://pixijs.com/8.x/guides/concepts/performance-tips), [texture resource guidance](https://pixijs.com/8.x/guides/components/textures), [prepare system](https://github.com/pixijs/pixijs/blob/dev/src/prepare/PrepareSystem.ts).

Depth sorting is already dirty-gated in [WorldDepth](../apps/client/src/world-depth.ts); it is not an unconditional full idle sort. Moving players dirty it as expected. Avoid changing it without a crowded-floor profile. Likewise, lowering DPR, removing antialiasing/shadows, or disabling animations changes visual behavior and is not a default optimization here.

The first pointer/key gesture initializes an AudioContext through [App.tsx](../apps/client/src/App.tsx), lines 775 onward, and [gong-audio.ts](../apps/client/src/gong-audio.ts). Source mapping attributed about 92 ms in the movement probe and about 516 ms in the editor probe to `getAudioContext`; device/browser initialization is variable. Evaluate separating initialization from the movement handler and performing gesture-required resume without delaying the first rendered response. Test actual autoplay rules and gong audibility; do not simply remove sound or assume an `async` function makes its constructor asynchronous.

Every world snapshot sets state in the workspace owner. A React profiling build should establish whether unrelated panels repeatedly render and how much that costs. If material, narrow snapshot subscriptions or provide stable imperative world updates; retain React state where the UI actually depends on positions. `useSyncExternalStore` can support selective subscriptions, but adding a store library alone does not prevent updates. No React commit-time breakdown was measured, so this remains a hypothesis. [React Profiler](https://react.dev/reference/react/Profiler), [external-store API](https://react.dev/reference/react/useSyncExternalStore).

**Network, persistence and meeting limits remain separate questions.** Bootstrap serializes all visible layouts/members/history, and `WorldRuntime.connect` sends another full bootstrap as `workspace.snapshot`. The fixture recorded 72,971 and 73,008 bytes respectively. A single versioned initial synchronization could avoid duplication; preserve reconnect repair and startup ordering. Server startup also loads many whole tables sequentially. In [app.ts](../apps/server/src/app.ts), dirty persistence runs every ten seconds and after some commands, cloning the workspace first. [synchronizeRows](../apps/server/src/persistence/synchronize-rows.ts) upserts all supplied rows and removes absent rows across the participating tables. Do not assume MikroORM change tracking makes those explicit upserts incremental. Measure with PostgreSQL before deciding between narrower domain writes and managed changesets. Database duration, locks, persistence write amplification, and server cold startup were not measured. [MikroORM unit of work](https://mikro-orm.io/docs/unit-of-work).

[MediaConnection](../apps/client/src/media-connection.ts) creates one `RTCPeerConnection` per other participant, with microphone, camera, screen and screen-audio transceivers. Eight participants imply seven remote peers per client and 28 pairwise connections, not eight streams passing through Fastify. Actual encoder sharing depends on the browser. Camera capture already requests 720p, ideal 24/max 30 fps; screen capture requests ideal 15/max 30 fps. ICE servers are configurable; deployed TURN/STUN configuration was not inspected. TURN path selection, uplink bandwidth, encode/decode load and jitter buffers can dominate independently of signaling speed.

Collect `getStats()` candidate-pair RTT/type/protocol, bytes and packet loss/jitter, `qualityLimitationReason`, frame drops/freezes, and interval deltas of encode/decode time per frame and jitter-buffer delay per emitted sample. Join time should distinguish server admission, ICE/DTLS and first playable media. Start with adaptation appropriate to visible media and measured device limits; consider an SFU only if target participant counts exhaust the mesh. An SFU adds bandwidth, hosting and operational costs and is not automatically lower latency for small nearby calls. [WebRTC statistics standard](https://www.w3.org/TR/webrtc-stats/), [mediasoup architecture](https://mediasoup.org/documentation/v3/scalability/).

For verification, collect p50/p95/p99 and outliers, not just average FPS. Use production assets with a profiling React build when measuring React itself. Record DOM shell readiness separately from WebSocket synchronization, first decoded avatar, required visible assets uploaded, and first interactive world frame. Browser resource/CPU/GPU tracks separate transfer, JavaScript, readback and rendering; server spans plus `monitorEventLoopDelay`/event-loop utilization separate handler work from queuing and database time. Measure RTT on one clock; subtract known server work only to estimate the remaining transport/queue contribution, not exact one-way delay from unsynchronized client/server clocks. [Loading phase guidance](https://web.dev/articles/optimize-lcp).

Use paired repeated trials on desktop, a lower-power GPU and the supported Android WebView; test crowded floors, many distinct avatars, floor cycling, build previews, games, meetings, simultaneous activity, and tab background/resume. Proposed initial guardrails are no new task over 50 ms during steady interaction, materially fewer frames over 33.4 ms, and server p99 comfortably below its 50 ms tick with headroom. These are validation targets, not claims of achieved improvements. Keep visual pixel comparisons and movement/game/media regression checks alongside the performance results.

Verification completed: production Vite bundling; source/delivery integrity checks for **1,702 originals and 5,104 delivery files**; lint for all four added scripts; strict TypeScript checks with the repository's optional-property/indexing settings for the typed probes; both dedicated browser scenarios with no page errors; server microbenchmarks; and the 40-tile image comparison. A hash comparison found no changes across **7,324 application source and image files** from inventory capture to the integrity check. Not verified: real network RTT/jitter/loss, production Nginx/CDN headers, PostgreSQL performance, real meetings/media, physical display/GPU timing or memory, native startup, sustained crowded-scene frame rate, the full application regression suite, or an integrated speedup from the proposed optimizations.
